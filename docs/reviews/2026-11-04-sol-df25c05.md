## 发现列表

### 1. [P2] summary() 成功仍不能证明共享账本可以接受预留

- 位置：`evaluation/collector/real_service.py:235-243`。
- 新检查读取实际共享账本，能拒绝前次的 `reservations (unexpected INTEGER)` 示例，也能拒绝累计预留达到 soft stop 的账本；但 `summary()` 只读取金额、计数与限额，不核验预留所需的其他列或实际写入能力。
- 合成复现 A：预先创建 `CREATE TABLE reservations (microyuan INTEGER NOT NULL)`。构造器的 `CREATE TABLE IF NOT EXISTS` 不修复已有表；`summary()` 返回合法的零余额快照，`create_real_app()` 成功返回应用。随后通过 `embedding_factory().embed()` 发起模拟请求，产品预留入口因缺少 `request_id` 列失败，返回 `ProcessingError: AI_PROCESSING_FAILED`；账本预留数和 MockTransport 请求数均为 0。
- 合成复现 B：预先创建 `CREATE TABLE zero_price_reservations (unexpected INTEGER)`。启动同样成功；即使当前使用付费报价，预留入口也会查询该表的 `request_id`，随后以同样方式失败。
- 写入能力对照：使用完整标准表结构，但增加拒绝 `reservations` 插入的合成 `BEFORE INSERT` trigger。启动仍成功，首个预留失败，模拟 HTTP 请求数仍为 0。这说明当前检查没有验证实际预留事务的写入路径。
- 影响：仍存在“共享账本已损坏/不可用于预留，启动却成功”的状态，前次第 1 项 P2 尚未完全关闭。请求层继续拒绝调用，本次未发现预算绕过或超支。
- 建议：返回应用前验证共享账本必需表结构与预留事务可用性；写入探针应回滚，不留下持久预留。失败统一转换为 `EVALUATION_SERVICE_NOT_READY: KNOWFLOW_BUDGET_LEDGER_PATH`，增加上述回归用例。

### 2. [P2] LLM 用例的错误输入被宽泛异常断言吞掉，未验证其预留路径

- 位置：`services/ai/tests/test_real_evaluation_service.py:242-253`，尤其是第 247 行的 `{"source_id": "s1", "text": "t"}`。
- 产品 `DeepSeekAdapter._payload()` 读取 `item["text_content"]`（`services/ai/src/knowflow_ai/answering.py:135-137`），在 `generate()` 调用 `reserve_provider_call()` 之前执行。当前测试输入触发 `KeyError('text_content')`，被 `pytest.raises(Exception)` 接受。
