## 问题证据与修复要求

### R1：live smoke 不受预算限制

`model_smoke.run()` 在凭证、模型和地址齐备后直接构造 urllib opener，`post_json()` 在第 104 行执行 `opener.open()`。此路径既不调用 `reserve_provider_call`，也不使用 `BudgetLedger`。它能发送 embedding 和 chat 请求，因此“所有真实调用路径都 fail-closed”尚不成立。

这是**基线已有、本区间统一预算接入时未覆盖的路径**，并非声称其 HTTP 代码由本区间新增。它属于本次明确要求核查的全仓库真实调用边界；`services/ai/tools/embedding_smoke.py` 则使用产品 embedding 适配器，已能继承新增预算检查。

离线复现：删除进程内三个 `KNOWFLOW_BUDGET_*` 配置，仅向 `smoke.run(env, 1)` 提供合成配置；用 `unittest.mock.patch` 将 `OpenerDirector.open` 替换为两个 `BytesIO` 合成响应。结果为：

```text
fake_opener_calls=2
status=LIVE_SMOKE_PASSED
exit_code=0
```

未发生网络请求。相同控制流在真实 opener 下会直接发出请求，预算已满也不会被此脚本检查。

修复要求：在此路径的每次 outbound attempt 前接入同一权威预算入口，或在真实模式下明确禁用该路径。补充“缺预算配置、达到软限额、超过硬限额时 opener 调用数为零”的测试。

### R2：真实评测调用会重复预留

`create_evaluation_app()` 启用的工厂始终返回 `GuardedEmbedding` / `GuardedLlm`。包装器在 `_reserve()` 写入 `eval:<uuid>` 后调用真实适配器；新增的底层预算入口随后再写入 `provider:<uuid>`。两者无关联，也没有一次尝试只能预留一次的机制。索引、query embedding、同步生成和流式生成都存在这组嵌套关系。

离线复现使用 `GuardedLlm(adapter_factory=lambda: DeepSeekAdapter(..., mock_client), ...)`，包装器与环境指向**同一个 SQLite 文件**。两层输入上界均为 10,000，输出上界为 1,024，合成报价为输入 1、输出 2 CNY/百万 token。MockTransport 返回 503，执行一次 `generate()` 后得到：

```text
mock_http_calls=1
paid_reservations=2
reserved_microyuan=24096
```

单次按该报价应预留 12,048 microyuan。失败保留一次预留符合保守预算设计，保留两次则是重复计数。相同配置下，评测会提前耗尽软预算；靠近上限时还可能发生外层预留成功、内层拒绝、没有发出 HTTP 却增加外层预留的情况。fake providers 没有底层 `reserve_provider_call()`，现有 fake 工厂测试的“一操作一条记录”无法覆盖这一组合。`estimate.py` 按 README 为每个供应商请求列一条记录时，也无法反映真实评测的双计。

修复要求：建立每次实际尝试唯一的权威预留边界，同时保留裸适配器的强制保护；不能通过简单跳过底层检查修复。对三种真实适配器加 MockTransport 组合测试，核对 HTTP 次数、预留次数、失败与重试，并使评测工厂和运行时引用同一账本配置。

### R3：fake E2E 缺少问答执行成功断言

`collect_question()` 会把 Java 非 200 且具备 trace 的请求转换为合法 `outcome="error"` 预测。`collect_dataset()` 只把收集过程中抛出的异常加入 `status.failures`；返回的 error 预测仍可得到 `complete=true`。这可用于保存执行错误样本，本身不等同于成功问答。

但 smoke 在第 103 行直接设置 `passed=True`，仅记录 `scorer["sample_count"]` 和预算摘要，没有要求 `metrics.execution_error_count == 0`，也没有断言 fake LLM 应产生的 answered 结果与引用。scorer 能正常评分含 error 的预测文件，调用 `evaluate()` 没有抛异常不能证明 upload→index→QA 全链路成功。

离线反例使用公开 seed 的 12 道 development 问题、合成索引映射和有效 trace；Java QA 全部返回 502。实际调用收集器和 scorer 得到：

```text
predictions: 12 个 outcome=error
status.complete=true
status.failures=[]
scorer.sample_count=12
scorer.metrics.execution_error_count=12
```

这组结果没有触发 smoke 当前的成功判断之外的任何质量断言。没有声称在本环境实际跑通了整个 Docker smoke。

修复要求：在 E2E 设置 `passed=True` 前断言预期样本数、零执行错误，以及 deterministic fake 的预期答案/引用；增加模型失败时 smoke 必须失败的负例。此外，保留单独的真实适配器 MockTransport 测试来覆盖 R2，fake E2E 不能替代它。

### R4：最后一题恰好达到软限额被误判失败

账本允许一次预留后总额**等于** 8,000,000，且成功后拒绝后续预留；但收集器每题写完结果后无条件检查 `>= 8_000_000` 并抛异常。这发生在最终完成标记之前，即使已经没有下一题也会触发。

离线复现：合成一个问题的公开数据子集，fake QA 成功返回合法 refusal，并使共享账本在该次操作达到 8,000,000。结果：

```text
predictions=[outcome=refused]
raised=BUDGET_SOFT_STOP
reserved_microyuan=8000000
complete=false
failures=[]
```

修复要求：只在仍有待执行工作时将达到软限额视为中止，或统一在下一次操作前检查；完整结果应能写入 `complete=true`。不得因此放宽账本拒绝超过 8 元的逻辑。
