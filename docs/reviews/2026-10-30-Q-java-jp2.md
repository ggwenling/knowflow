## Q-JP2-J01 · P2：按裸 source_id 替换会破坏正文和其他引用

位置：`services/api/src/main/java/com/knowflow/api/answer/QuestionService.java:196`。

`publicAnswer.replace(source.sourceId(), publicSourceId.toString())` 对整个字符串逐个执行，而合法 ID 允许 `a`、`s1`、`s10`。因此 ID 出现在普通词中会被替换；短 ID 是另一 ID 的前缀时，后者会提前被破坏。此时接口仍返回 200，错误答案还被记录为 SUCCEEDED。

使用真实 PostgreSQL/MinIO，完成上传、索引发布和问答请求，HTTP AI fixture 返回三个有效来源，ID 分别为 `a`、`s1`、`s10`，正文为 `data [a] [s1] [s10]`。实际正文中的 `data` 变成 `d<UUID-a>t<UUID-a>`，最后一个引用变成 `[<UUID-s1>0]`，不再对应 sources 中的 UUID-s10。来源版本、Chunk、定位和引用原文均合法，失败来自本地转换。

建议：先构建完整 ID 映射，再按契约规定的引用标记边界一次性解析替换；不替换普通正文，也不让已经生成的输出参与后续替换。回归覆盖短 ID、前缀重叠和普通词中出现 ID。

## Q-JP2-J02 · P2：对象正文读取没有生效的超时

位置：`services/api/src/main/java/com/knowflow/api/storage/S3ObjectStore.java:99–112`，核心阻塞点为第 111 行。

`BodyHandlers.ofInputStream()` 在收到响应头后交回输入流；请求上设置的 10 秒 timeout 不覆盖之后的 `readNBytes`。若存储已发送 200 和部分正文，但后续停滞且连接保持打开，读取没有应用层截止时间。`SourceReadService.read` 和 `DocumentService.readFile` 在持有数据库事务与文档锁时调用它，内部源读取还持有任务锁，因而阻塞 heartbeat、删除及相关状态写入；并发请求可长期占用连接池。

独立本地 HTTP server 声明正文 2 字节，只发送第一个字节后等待。在未修改的目标编译类上调用 `getObject`，**12,209 ms 后仍阻塞**；放行第二个字节后正常返回 2 字节，证明 10 秒配置没有使正文读取超时。复现没有访问真实存储或使用真实凭证。

建议：为完整响应正文设置可取消的读取截止时间，超时时关闭输入流并让事务回滚，同时保留现有大小限制。回归覆盖响应头及时返回、正文停滞的情况。

## Q-JP2-J03 · P2：MinIO 健康探测可能在初始化重启前就放行测试

位置：`services/api/src/test/java/com/knowflow/api/document/DocumentApiIntegrationTest.java:114`；`S3ObjectStoreIntegrationTest` 使用同类等待方式。

固定的 Bitnami 镜像会先启动后台 MinIO 执行初始化，再停止并正式启动。单次 `/minio/health/live` 成功可能命中后台进程，不能证明初始化结束。本次未改动源码的 `verify` 因两个上传请求得到 503 而失败；日志中上传失败与 `Stopping MinIO` / 正式启动时间重叠。

原失败用例为 `completionVerifiesStoredRowsAndPublishesAtomicallyAndIdempotently` 和 `retryableCompletionFailureRequeuesForANewFencedCandidate`。在一次性副本中仅加强启动屏障，等待正式启动日志后再等待 HTTP 健康，这两项均通过；同轮新增的引用回归仍按 J01 预期失败。正式源码没有应用该测试改动。

建议：让两个存储测试 fixture 等待最终启动阶段及健康状态，避免 `verify` 随初始化时序失败。
