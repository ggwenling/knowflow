# KnowFlow V0.2 项目计划书

**修订日期：** 2026 年 10 月 29 日  
**项目定位：** 面向小型研发团队文档查询场景的 AI 知识库技术实践；首版以个人账号、知识库所有者隔离验证核心能力  
**执行编制：** Codex-A、Codex-B、Muse 三条研发主线 + 一个 Code Review Agent  
**版本关系：** 本文替代 V0.1 的项目范围、排期与协作安排；已有 V1.1 技术设计包继续作为待核对的数据库/API 基线  
**配套文件：** [细分任务](./KnowFlow_V0.2_任务拆解.md)、[Agent 协作手册](./KnowFlow_V0.2_Agent协作手册.md)、[任务表 CSV](./KnowFlow_V0.2_任务表.csv)

> 本次交付是计划修订，项目代码、源码调研、用户访谈、评测及部署均未执行。原文提到的 `knowflow_v1_design_pack.zip` 未提供，不能宣称已与其兼容。下文的技术与产品选择是提议基线，需要通过 KF2-001～004 核对后形成实施契约。

## 一、项目目标与价值假设

### 1.1 首先服务谁

首轮验证聚焦：**需要反复查询中文技术说明、项目规范和故障记录的小型研发团队成员。** 首版允许不同用户各自管理知识库，不包含团队共享与成员角色。学生研究者、通用个人知识管理作为后续候选场景。

待验证的问题：资料分散时，用户查找答案及核对依据耗时；文档更新后容易引用过期内容。首版围绕一条流程交付：**上传真实资料 → 查询一个具体问题 → 查看支持回答的原文 → 更新或删除文档后查询结果正确变化。**

这一定位是待验证假设，不是已完成的市场结论。它与团队协作功能的延期并不冲突：先验证团队成员查资料的个人任务，再验证是否需要共享工作空间。

### 1.2 三类价值分别验收

| 目标 | 需要的证据 | 不足以证明目标的材料 |
|---|---|---|
| 技术成长 | 独立解释权限、任务恢复、索引版本、检索及引用的设计取舍；有失败案例与实验 | 只列技术栈、只展示 Agent 生成的代码 |
| 可展示的工程作品 | 可部署源码、真实端到端记录、隔离测试、检索评测、问题修复记录 | 只有界面截图或录屏 |
| 用户使用价值 | 真实任务耗时、正确性、核验成本和持续使用记录 | 只问“你觉得这个功能好吗” |

项目启动以技术成长和工程交付为确定目标；长期产品化与商业化根据试用结果另行决策，不预设付费需求已经成立。

## 二、交付范围与验收边界

### 2.1 M1：首个真实闭环，目标窗口第 3—4 周

1. 基础注册/登录、当前用户、个人知识库；所有 API 强制所有者隔离。
2. 上传前可见选定的模型数据去向、隐私模式和基本格式/规模限制；上传 TXT、MD、文本型 PDF，异步解析、分段、Embedding，页面可查看状态和失败原因。
3. 对当前用户有权访问的一个知识库执行向量检索、单轮问答；首闭环允许非流式回答。
4. 回答引用具体文档、索引版本、Chunk 和可用的页码/原文片段；点击可核验。
5. 文档逻辑删除后，新检索、引用详情、原文预览均不可访问；迟到任务不能恢复文档。
6. 用两个用户和真实模型完成端到端验收。Mock 或固定答案只用于开发，不能算闭环通过。

### 2.2 V1：稳定且可部署的工程版本

在 M1 上增加：索引更新与原子切换及其页面入口、任务租约/幂等/恢复、SSE、问答记录与列表、PDF 页码定位、明确的文件边界、部署与恢复说明、评测与安全回归、首轮试用结论。

**问答记录不等于多轮上下文：** V1 可展示历史问答，但每次检索基于当前完整问题；界面明确提示，跨轮指代与 Query Rewrite 后移。

### 2.3 V1.5 候选项，默认不阻塞 V1

团队成员/RBAC、DOCX、中文关键词检索 + RRF、Rerank、多轮上下文、PDF 精确区域高亮、参数调试界面。每项单独立项，不要求一次全部完成。

不开发：复杂 Agent 编排、OCR/多模态理解、SSO、计费、Kubernetes、大型分布式架构。

**裁剪顺序：** 优先延期 V1.5 → 简化历史与预览样式 → 简化 SSE 体验；安全隔离、真实索引、证据核验、恢复与部署底线不能靠删验收解决。任何 V1 范围变化要记录理由并更新版本完成定义。

## 三、四个 Agent 的职责

| 角色 | 主线交付 | 默认修改所有权 | 协作责任 |
|---|---|---|---|
| Codex-A（A） | Java API、认证与资源权限、文件元数据、索引任务调度、业务状态、版本发布、会话记录、SSE 网关 | `services/api/`、Flyway、公共契约、架构 ADR | 兼任集成协调者，安排共享文件修改与合并次序 |
| Codex-B（B） | Python 解析、Chunk、Embedding、检索、证据生成、流式生成、评测与算法实验 | `services/ai/`、`evaluation/`、对应研究记录 | 提供可复现输入输出，报告模型成本、边界与失败原因 |
| Muse（M） | Next.js 页面、上传/状态/问答/引用/历史体验、Compose、CI、端到端测试与试用支持 | `apps/web/`、`infra/`、`.github/`、`tests/e2e/`、用户验证记录 | 从第一阶段交付主线功能；提前用契约 Mock 开发，持续真实联调 |
| Code Review Agent（Q） | 契约、代码、测试证据、集成结果、候选版审阅 | `docs/reviews/`；默认不改实现代码 | 输出可操作问题，按提交复核修复；不接替主线研发 |

以上是执行角色，Muse 使用团队实际可用的 Muse Agent；不能由另一个模型静默代替并声称 Muse 已执行。若执行环境无法调用其中一个角色，记录能力缺口后再安排执行方式。本计划不意味着四个 Agent 已启动或代码已完成。

### 3.1 并行方式

- 契约冻结后，A 写 API，B 写 AI 能力，M 写页面及基础设施，Q 滚动审阅。
- 真实验收依赖不能通过 Mock 解除；开发提前量与验收依赖分开记录。
- 三个主线 Agent 各自最多一个正在开发任务、一个待审任务。待审积压时先修复或联调，降低新任务启动速度。
- 每个 Agent 在独立分支/worktree 开发；共用同一目录时严格遵守文件所有权，不能假设分支提供文件隔离。
- 每次提交围绕一个可验收任务；最终合并由 A 协调，避免三条主线同时改变集成基线。
- 不按“四个 Agent 等于四倍速度”估算。契约、合并、审阅和真实反馈构成共同约束。

## 四、技术架构与数据流

### 4.1 技术栈

| 层次 | 基线 | 说明 |
|---|---|---|
| 前端 | Next.js、React、TypeScript、Tailwind、shadcn/ui、TanStack Query | PDF.js 在需要页码预览时接入 |
| 对外 API | Java 21、Spring Boot、Spring Security、MyBatis-Plus、JWT、WebClient、Flyway | 统一鉴权、业务状态与对外协议 |
| AI 服务 | Python 3.12、FastAPI、PyMuPDF；LangChain 按需使用 | 2-Step RAG；不为了使用框架而增加抽象 |
| 数据与部署 | PostgreSQL + pgvector、MinIO/S3、Docker Compose、GitHub Actions | 基础版本暂不引入 Redis；FTS 进入中文混合检索实验后再评估 |

依赖版本在兼容性任务中锁定并记录，不把未验证的大版本组合视为已可用。PDF 解析库等第三方依赖的许可在选型时登记；涉及分发与商业使用的具体约束，核对实际版本和许可文本。

保留 Java + Python 是为了训练业务工程与 AI 工程协作能力，同时承认接口、鉴权传播、流式转发和部署带来的额外工作。

### 4.2 数据所有权与异步协议

建议基线，经原设计包核对后落地：

1. **A/Java 是业务状态唯一写入方：** 用户、知识库、文档、任务状态、活动索引版本、会话；Flyway 统一负责结构迁移。
2. **B/Python 是 AI 执行方：** 在受限数据库角色下写指定索引版本的 Chunk/向量；不得直接修改文档状态或发布活动版本。
3. Java 领取任务、生成租约与执行令牌，派发给内部 Python；Python 心跳与完成结果由 Java 按当前租约验收。具体接口在 KF2-004 固定。
4. 幂等身份至少包含文档、内容版本、流水线配置版本；旧租约的回调、删除后的回调和不匹配版本的结果必须拒绝。
5. 索引完整后，由 Java 在事务中切换活动版本；新版本失败保留旧版本。删除立即撤销逻辑可见性，物理对象和索引由可重试清理流程回收。
6. 明确 Chunk、向量、任务回调三者的一致性及清理机制，避免“索引写入成功”被误当成“业务已经发布”。

### 4.3 权限、删除与历史引用

- 浏览器仅访问 Java。Java 校验身份、知识库、文档与当前状态，内部调用携带经验证的资源范围与服务认证；不能相信前端提交的资源 ID。
- Python 查询必须在 SQL/检索层限定资源范围、活动版本和未删除状态；回答、缓存或批量查询不能绕开过滤。
- 引用详情、原文预览和下载均再次鉴权；避免可长期复用的公开对象链接。首版优先通过鉴权 API 代理访问文件。
- 请求开始时确定一个一致的活动版本快照。新版本切换前已接受的请求可按该快照完成；切换后的新请求只能使用新活动版本。
- 删除提交后开始的新请求不能检索、查看原文或引用。进行中的回答在输出答案/来源前再次检查可见性，SSE 在每次向客户端发送事件前检查；发现已删除则终止。删除前已到达客户端的内容无法撤回，此边界写入说明。
- 历史问答中已显示的文本不自动消失；被删文档的来源显示“已删除/不可访问”，不能借历史引用下载原文。索引更新后的旧引用绑定旧版本，按保留策略显示，不伪装成新版本证据。
- V1 没有成员撤权；团队共享扩展时复用同样的新请求、历史访问、运行中请求语义并增加成员撤权测试。

### 4.4 公开的输入与资源边界

KF2-003/004 必须记录文件大小/页数/字符数上限、知识库文档量、并发索引数、模型上下文、超时、重试上限、目标机器配置及是否使用 GPU。初始值通过真实样例验证后确定，不能预先承诺任意规模。

- 仅支持文本型 PDF；扫描件、加密文件、空文本、严重多栏/表格解析失败要明确反馈。
- PDF 引用提供页码与文本片段；TXT/MD 提供段落/字符定位。没有可靠定位信息时不能编造页码。
- 上传文件、解析器、日志和模型调用设置资源与内容边界；文档中的指令只作为资料，不得覆盖系统规则或扩大访问范围。

## 五、隐私、模型与运行成本

**“私有”需要明确模式：**

| 模式 | 数据流 | 要求 |
|---|---|---|
| 本地存储 + 外部模型 | 文档本地保存，但文本/检索片段可能发给 Embedding、Rerank 或 LLM 服务商 | 列明供应商、发送内容、日志策略与费用；界面明确说明 |
| 全本地处理 | Embedding、Rerank（若启用）、LLM 全在约定环境运行 | 在目标硬件实测资源和延迟；不能用外部模式结果证明本地模式性能 |

首个闭环只承诺 KF2-003 选定并实测的一种配置，另一种后续独立验证。密钥不进入仓库、浏览器与日志。离线演示/Mock 必须显式标识，不能伪装成真实模型验收。

记录每文档索引费用、每问答 token/费用、解析和索引耗时、检索与首 token/完整回答延迟；设置可配置的请求和并发上限。具体额度由实际供应商、样本文档与目标设备决定。

十周是参考窗口。当前未知每周人工投入、原有代码完成度和 Muse 的实际执行环境；第一周记录人工协调时间、每个角色活跃工作量、审阅周转及真实任务吞吐，再修订预测。Agent 工作时段不能直接等同于人工工时。

### 6.1 基线缺失时可以做什么

KF2-001 标记待输入，保留冲突与假设清单。用户研究准备、模型试验、解析样例、隔离的骨架/Mock 可以先推进；依赖正式 Schema 的迁移和业务接口不能宣称已获兼容性验收。拿到设计包后补齐映射，禁止未经审查创建第二套“正式基线”。

## 七、RAG 研究与质量评测

### 7.1 开源研究继续保留，但绑定任务

- RAGFlow：解析/分段绑定 KF2-016/017，检索/生成绑定 KF2-021/022，混合/Rerank 绑定增强任务。
- MaxKB：鉴权/实体绑定 KF2-012/013，上传/任务绑定 KF2-014/015，状态和界面绑定 KF2-020/034。
- 每个主题输出一条经核验调用链、一个最小实验、一个采纳/修改/不采纳结论；记录实际 Tag/Commit、路径与入口。每个主题设研究预算，耗尽后带结论或待研究项回到交付。
- 最终汇总两份研究报告；不要求为了阅读源码部署完整参考项目。
- 参考项目与本项目第三方依赖均建立许可证清单，不未经评估复制代码。

### 7.2 评测数据和指标

先以 10 份合法文档、15 道种子问题建立脚手架，M3 前扩展到至少 60 道人工核验问题。建议 40 道用于开发、20 道固定留出验证；保留集不用于调参，若据其错误继续调整，则标注污染并补充新样本。

问题分层沿用：事实 15、改写 15、多证据 10、中文关键词/同义词 10、无答案/干扰 10。每类在开发与留出集均有样本。权限负例单独建回归，不混入相关性指标抬高成绩。

标准证据以文档内容版本、页码/字符区间和原文片段为基准，再映射到具体 Chunk；跨切分方案不直接复用 Chunk ID 作为唯一真值。无法回答题明确无证据，跨文档题标注完整证据集合。

V1 固定向量基线；V1.5 才比较 A 向量、B 混合+RRF、C 混合+Rerank。固定文档/模型/参数，记录 Recall@5、MRR@10、多证据完整性、关键结论证据支持率、拒答正确率、p50/p95、费用。小数据集的结果只说明该集合表现，不当作普遍准确率承诺。

M1 后在开发集建立并登记首个质量/延迟阈值；M3 用固定留出集判断，禁止看到最终结果后追改阈值。基线差时允许缩小支持场景并明确失败类型，不用模糊“已达标”替代数据。

## 八、真实用户验证

M1 前由项目负责人招募或安排 3—5 位同类用户；M 负责原型与记录工具。未经明确授权，Agent 不自动给外部联系人发邀请或消息。

M1 后试用至少两周，在相同资料、任务上对比原有查找方法与 KnowFlow，记录任务成功率、正确依据定位时间、核验成本、错误严重性、主动复用及流失原因。参与者接触的资料必须有权使用；以匿名或获准文档起步。

记录实际完成多少用户、多少任务、观察多少天；没有参与者或观察期不足就标记“未验证”。用户访谈脚本和假设推演不能替代证据。

结果用于三个选择：继续当前场景；调整场景/功能；停止产品化但保留技术作品。若考虑商业化，额外验证愿意付出的金钱、部署或维护成本，不从好评推导付费意愿。外部试用未完成可以交付明确标记的技术候选版，不能宣称产品价值已验证，也不能把 M3/M4 的完整门槛标成通过。

## 九、质量、审阅与版本治理

1. 采用小批量任务卡，写清依赖、范围、契约、边界、验收、测试与禁止修改范围；详见任务拆解与协作手册。
2. 作者提交代码、测试命令/结果和目标 SHA；Q 审阅具体基线到目标的差异，区分阻断、非阻断与待验证问题。
3. 修复与冲突处理产生新代码后，复核变更及相关影响；合并后的实际集成状态运行约定检查，不能用旧 SHA 的结论覆盖新代码。
4. 安全、权限、数据一致性、错误来源、不可部署属于阻断项。无关风格建议单独排队，避免审阅无限扩散。
5. 共享文件单写：公共 Schema、Flyway、ADR 归 A；Compose/CI 归 M；B 提交索引结构和模型接口需求，由 A 合并契约后实施。
6. 新任务使用 `KF2-*`；不改写旧 `KF-*`。KF2-001 建立多对多映射和替代原因，旧任务完成状态需查代码/测试证据确认。
