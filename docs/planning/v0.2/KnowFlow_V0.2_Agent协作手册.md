# KnowFlow V0.2 Agent 协作与派工手册

**执行编制：** 2 个 Codex Coding Agent + 1 个 Muse 主线 Agent + 1 个 Code Review Agent。  
**用途：** 给实际执行环境配置角色、派工和验收；本文本身不表示 Agent 已启动。  
**配套：** [项目计划](./KnowFlow_V0.2_项目计划书.md)、[56 项细分任务](./KnowFlow_V0.2_任务拆解.md)。

## 一、执行前准备

1. 核对是否已有代码仓库、分支、AGENTS.md 和 V1.1 设计包；记录实际路径与版本，不先建立第二个正式仓库。
2. 确认两个 Codex、一个真实 Muse 和一个独立审阅 Agent 可用。角色名称与模型身份分开记录，不因工具名称相近推断模型相同。
3. 在正式仓库中建立任务与审阅记录；本交付包里的路径是建议结构，现有结构优先。
4. 原设计包未附本次材料，因此 KF2-001 的兼容性验收当前缺输入；模型凭证、目标设备和用户参与情况也未核验。可以先做准备工作，不伪报 READY/DONE。
5. 确定同一时区与环境配置。记录时间统一带时区；当前项目文档日期按 Asia/Hong_Kong 使用 2026-10-29。

## 二、职责与文件所有权

| 角色 | 必须直接交付的主线 | 默认写入范围 | 不自行修改 |
|---|---|---|---|
| A / Codex Coding 1 | Java业务、权限、任务与版本、问答网关 | `services/api/`、`contracts/`、Flyway、架构 ADR | Python业务、前端、Compose/CI |
| B / Codex Coding 2 | AI解析、索引、检索、生成、评测 | `services/ai/`、`evaluation/`、RAGFlow研究记录 | Flyway、任务业务状态、前端、公共契约 |
| M / Muse | 前端产品主线、联调、基础设施和E2E | `apps/web/`、`infra/`、`.github/`、`tests/e2e/`、产品/交付记录 | 后端授权、任务状态机、数据库迁移、AI算法 |
| Q / Code Review | 独立代码和证据审阅 | `docs/reviews/` | 主线实现、无关重构、作者尚在编写的文件 |

A兼任集成协调者，不额外增加第五个Agent。MaxKB研究按主题由A提供业务/任务记录、M提供界面记录，最终由M汇总引用；原始记录仍由实际作者负责。

**共享文件规则：**

- 公共契约由A提交；B/M提交字段需求、示例或变更提议，不能各自提交不兼容版本。
- Flyway仅A分配版本并提交。B提供所需向量/全文结构和数据库角色需求，A落地迁移，Q检查。
- Compose、CI、根锁文件若由M维护，A/B只提交服务要求，由M集成。每个服务自己的依赖锁文件仍归该服务所有者。
- 所有权表可以通过显式交接调整，记录任务、文件、交接时段与当前提交；不能同时拥有写入权。
- 可选项如中文分词新增DDL，先补建A的迁移子任务，再让B完成真实集成；父任务不能用未合并的DDL建议当作完成。

## 三、分支、工作区与集成

### 3.1 推荐方式

每个Agent独立worktree/工作目录，任务分支从同一已知集成基线创建。例如 `agent/a/KF2-014-upload`、`agent/b/KF2-018-index`、`agent/m/KF2-020-upload-ui`。采用仓库既有分支规范时沿用现有名称。

Agent记录自己的基线SHA、当前分支和worktree路径。若工具只提供一个共享目录，同一时段仅在各自文件范围修改，并序列化切分支/合并；不能一个Agent切分支影响另外两个正在编辑的工作区。

### 3.2 一项任务的流转

1. 作者核对依赖、契约和所有权，将任务移到READY，再进入IN_PROGRESS。
2. 完成一个小目标，运行适用检查，提交可审阅差异；记录失败和未执行项。
3. 提交审阅包，进入IN_REVIEW；Q按基线和目标SHA审阅，输出问题与适用范围。
4. 作者处理阻断项，提交修复SHA；Q复核修复及其影响，不机械重做无关全量审阅。
5. 获APPROVED后，A协调合并顺序；原作者或M对实际集成状态执行约定检查。
6. 冲突解决或合并后代码产生新变化，回Q审对应差异；集成验证通过才DONE。

不覆盖其他Agent未提交的修改，不用强制重置清理共享工作区。没有任务要求时不进行外部发布；本轮只修改计划文档。

### 3.3 控制审阅排队

- 每个主线Agent最多一个正在开发、一个待审任务。
- Q优先：阻断其他主线的契约/迁移 → 权限/任务/版本一致性 → M1真实集成 → 普通页面/文档。
- 通常一次审一个任务或一组不可拆分的小变更，避免等整周结束才交一个大PR。
- 有待审任务时，可以做不依赖其通过的研究或下个小任务；当待审达到上限，先修复、补证据、支持联调，不持续扩大队列。
- 同类问题批量反馈，阻断项一次尽可能说完整；无关风格建议不扩大当前任务范围。

## 四、契约变更与Mock使用

### 4.1 契约先行

契约至少包含：身份与资源范围、请求/响应及错误码、任务租约与幂等、索引版本/发布、证据定位、删除/失效、SSE及取消、历史记录边界。

变更流程：提议者写原因/兼容性/影响任务 → A更新草案 → B/M确认消费方式 → Q审高风险边界 → A发布新版本 → 各所有者实施。紧急修复也要补齐受影响任务和Schema，不另开隐式协议。

### 4.2 可以提前并行的内容

| 条件 | A | B | M |
|---|---|---|---|
| 设计包尚缺 | 映射清单、提议状态机、隔离骨架 | 模型/解析样本、资源与许可核对 | 场景脚本、静态页面、仓库/CI草案 |
| 契约已冻结，API未完成 | 实现业务与迁移 | 按真实Schema开发AI接口与测试夹具 | 以同一Schema的Mock做页面和错误态 |
| 首批接口可用 | 修复业务边界 | 真实模型和索引联调 | 逐个替换Mock，不等所有后端完成 |
| M1后 | 恢复/版本/历史/SSE | 解析加固/质量/成本 | 页面完善、部署与真实试用 |

Mock应标注来源、契约版本和启用方式；生产默认关闭。任务卡的硬依赖决定真实验收顺序，Mock仅提供开发提前量。

你是KnowFlow主线M（Muse Agent），承担完整研发主线，负责Next.js页面、上传/状态/问答/引用/历史体验、Compose、CI和端到端联调。

### 5.4 Code Review Agent

```text
你是KnowFlow独立Code Review Agent（Q），负责审阅，不接替A/B/M实现。
先读取仓库AGENTS.md、V0.2计划、当前任务卡及适用契约。
当前任务：<KF2-ID>；审阅范围：<BASE_SHA>..<TARGET_SHA>；作者：<A/B/M>。
核查需求与依赖、实际代码、测试/数据证据；重点看权限、任务租约/幂等、版本切换、删除/历史、引用支持、隐私与可部署性。
输出可复现触发条件、影响、代码位置和验收建议；区分阻断、非阻断与待验证，避免无关风格重构。
默认不改实现代码，问题交还作者。必要时自行运行与问题相关的检查，不能只采信作者摘要。

没有足够证据时给BLOCKED或CHANGES_REQUESTED，不猜测通过。
最终分别判断工程候选版可交付、完整项目是否含真实试用证据，不能把技术完成等同产品价值已验证。
```

## 七、第一轮派工与依赖交接

| 顺序 | A | B | M | Q |
|---|---|---|---|---|
| 第一批 | KF2-001；缺设计包则记输入阻断并整理提议 | KF2-003 | KF2-002，随后005 | 审职责/假设/数据流与边界 |
| 契约轮 | KF2-004；B/M提供字段需求 | 支持004，准备010资料 | 支持004，准备布局与基础设施 | 优先审004并一次汇总阻断项 |
| 骨架轮 | 006、011依次推进 | 007、010依次推进 | 008、009依次推进 | 检查权限与三端可启动证据 |
| 闭环轮 | 012→013→014→015→019→023→024 | 016→017→018→021→022 | 020/025提前Mock，按接口替换；026真实验收 | 每批审阅，优先跨主线阻断项 |

此表只给工作方向；每张任务卡的硬依赖、WIP和所有权规则优先。例如009需要三个服务骨架完成，020可以先开发但不能在019真实接通前验收。

**固定交接证据：**

- A→B：租约/任务载荷、受限数据库角色、当前契约和错误样例。
- B→A：解析/索引清单、心跳/结果样例、失败类型与真实调用记录。
- A/B→M：可调用地址、鉴权方式、契约版本、成功/失败样例和服务配置。
- M→A/B：请求ID、浏览器操作、实际响应、期望行为和复现步骤。
- 全体→Q：最小任务差异、具体SHA、依赖、验证证据与未解决项。

## 八、阻断处理与阶段结束

- 依赖阻断：写清缺什么、谁能解除、哪些准备工作仍可做；不空等，也不绕过正式验收。
- 审阅阻断：作者先修问题，Q按实际修复复核；不通过重命名任务或换Agent消除问题。
- 契约冲突：A组织最小ADR，B/M提供消费影响；未冻结前隔离开发，避免三端各自猜测。
- 进度落后：停止可选增强，优先解决M1或当期门槛；记录实际吞吐后调整排期。
- 每阶段结束记录：已完成/未完成、真实证据、阻断、花费、下一阶段READY任务。没有新增证据时不反复扩大测试或研究范围。

最终以KF2-044记录审阅结论；KF2-041另判产品试用完成度。工程候选版可以先交付，产品价值保持诚实的证据状态。
