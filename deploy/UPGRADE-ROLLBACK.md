# 升级与回滚（草案）

状态：`DRAFT / NEVER EXECUTED`。`docs/operations/backup-restore-acceptance.md` 明确记录：**升级失败回滚与数据库降级尚未验证**。本文件写的是设计意图，不是已验证的步骤。

## 1. 硬边界：数据库不降级

- 迁移由 Flyway 管理，当前 `V1` … `V8`，**全部 forward-only**，仓库内无 undo/down 脚本。
- 因此"回滚"只有两种：
  1. **应用回滚**（镜像回退）——可行，前提是新版本没有写入旧版本不认识的数据。
  2. **数据回滚**（恢复到备份点）——可行，但**会丢掉备份点之后的所有写入**。
- 不存在"数据库降到上一版 schema"这条路。任何要求降级的场景，正确动作是恢复备份 + 明确告知数据丢失窗口。

## 2. 升级流程

前置：`PRODUCTION-CHECKLIST.md` G1–G4 已完成，且已有一个校验过的备份。

```
1. 冻结写入
   - 通知使用者停写，或临时把 web 从反代摘掉（保留 api 供内部检查）
2. 基线备份
   - pg_dump（含 schema + data）→ 记录 SHA-256
   - MinIO 归档（对象前缀全量）→ 记录 SHA-256
   - 记录当前 flyway 最高版本
3. 拉取新镜像并记录 digest
   - docker compose pull（或 build），docker images --digests 存证
4. 只跑迁移
   - docker compose --env-file <env> -f deploy/compose.production.draft.yml run --rm migrate
   - 退出码必须为 0；非 0 立即停止，不要重启 api
5. 滚动应用
   - api → ai → web（顺序不可颠倒：web 依赖 api healthy，api 依赖 ai healthy）
6. 验证
   - /actuator/health = UP
   - /health/live = UP（ai）
   - 一次完整问答（含来源打开）
   - flyway 版本 = 期望值
7. 解除冻结
```

## 3. 失败模式与处置

| 失败点 | 现象 | 处置 | 数据影响 |
|---|---|---|---|
| 迁移脚本报错 | `migrate` 退出码非 0 | **停止**。Flyway 在该版本处中断，未提交的事务回滚。修复脚本后重跑，或恢复备份 | 无（迁移事务级回滚） |
| 迁移成功但新 api 起不来 | api 容器反复重启 | 应用回滚到上一镜像；schema 已是新版，旧 api 若兼容则可运行，不兼容则走备份恢复 | 取决于兼容性 |
| api 起来但 AI 报 401 | `INTERNAL_SHARED_SECRET` 不一致 | 修正环境变量后重启 api 与 ai | 无 |
| 索引任务全部失败 | `INDEX_WRITE_FAILED` | 检查 ai 数据库角色权限与对象存储连通性 | 无（任务可重试） |
| 上线后数据异常 | 业务查询结果错乱 | **不要**尝试降级 schema；停写 → 恢复备份 → 接受丢失窗口 → 复盘 | 丢失备份点之后的写入 |

## 4. 兼容性窗口

- 目标：支持"上一版 api + 新版 schema"至少一个发布周期（N / N+1）。
- 现状：**未验证**。V8 之后没有跨版本共存测试，`docs/architecture/compatibility.md` 描述的是契约兼容性，不是数据库兼容性。
- 结论：首次上线应视为**单版本**部署，升级时接受短暂停写，不做真正的滚动升级。
